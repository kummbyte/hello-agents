## 3. 风险与假设

**假设**
- A1：85% 是行覆盖率；若为分支覆盖率，实际质量更高，可放宽收尾要求。
- A2：模型层对外接口已稳定、不再变动。
- A3：模型层无未关闭的 blocker（**我无法验证，需你确认**）。

**风险**
- R1（高）：覆盖率 ≠ 有效性。快照测试、无断言测试会虚高数字，无法为业务层重构提供安全网。
- R2（高）：模型层若保留兼容/双写层，进入业务层后会集中暴露，导致返工。
- R3（中）：业务逻辑层往往缺少现成测试，直接重构等于"无网走钢丝"。
- R4（中）：模型层接口未冻结就往下走，后续变更会同时冲击两层。

## 4. 下一步行动建议

**Step 0 — 补齐信息（需你提供）**
1. 当前 blocker / TODO 清单（我会按优先级排序）。
2. 覆盖率报告明细：分支覆盖率、变更覆盖率，以及测试是否有断言。
3. 模型层接口冻结清单（对外 API / DTO / 迁移脚本）。

**Step 1 — 模型层收尾（预计最小成本，收益最高）**
- 对核心模型路径补充**分支覆盖**，并做一次变异测试抽样，验证测试"能失败"。
- 冻结模型层接口，打 tag / 版本标记，冻结后变更需走评审。

**Step 2 — 建立回归基线**
- 全量测试 + 关键链路端到端用例跑通并留存结果，作为业务层重构的对照基准。

**Step 3 — 业务逻辑层重构（建议顺序）**
1. 先写**特征测试（characterization tests）**锁定现有行为，覆盖率目标设在业务层核心用例上，而非全量行数。
2. 按「数据访问 → 领域逻辑 → 编排/调度」分层解耦。
3. 小步提交，每步保持行为等价；以"覆盖率不下降 + 基线用例全绿"作为合并门槛。

**判断点**：若 Step 0 中出现模型层相关 blocker，**优先清 blocker 再往下走**；若模型层接口未稳定，建议把业务层重构拆成"先隔离适配层、后重构内部"两阶段，避免双向耦合。
